## Decisions

### 1. Vault Architecture: Single Vault

One vault for everything (`zbrain-vault`). No per-project vaults.

**Rationale:** MuninnDB's Hebbian learning forms associations from co-retrieval. Splitting vaults kills cross-domain connections — the core value of cognitive memory. Decay handles noise (irrelevant stuff fades). Can split later if needed.

**Implication:** All `capture` calls write to the same vault regardless of domain. Domain filtering happens at query time via tags, not vault separation.

### 2. Retrieval Strategy: Parallel Trial

Both pgvector search (libSQL/MuninnDB) and ACTIVATE (MuninnDB) run during a 1-2 week trial period. Compare results side by side, then pick a primary with the other as backup.

**Rationale:** MuninnDB is alpha software. Going all-in immediately risks losing retrieval if it breaks. Running both lets us evaluate quality with real usage data.

**Implication:** The `search` MCP tool returns results from BOTH systems during trial, clearly labeled by source. After trial, switch to winner as primary with fallback to the other.

### 3. MCP Tool Surface: Brain Wraps Everything

Brain MCP server stays the single gateway to Claude. MuninnDB's own MCP server (port 8750) is NOT registered with Claude.

**Rationale:** If Claude writes to MuninnDB directly AND through brain, memories desync. Wrapping through brain guarantees dual-write consistency and keeps the tool interface simple.

**Implication:**
- `capture` → modified to dual-write (libSQL/MuninnDB + MuninnDB) internally
- `search` → modified to query both systems during trial period
- New tool: `activate` → MuninnDB cognitive retrieval (ACTIVATE pipeline)
- No other new tools initially. 12 existing tools + 1 new = 13.

### 4. Embedder & Enrichment: Gemini, No Enrichment

Use Google Gemini embeddings (`MUNINN_GOOGLE_KEY`) matching the libSQL/MuninnDB model (`gemini-embedding-001`). No LLM enrichment.

**Rationale:** Consistent embeddings between systems. Hebbian learning builds the graph from usage patterns — that IS the cognitive feature. Paying for LLM enrichment on every write is redundant with existing `brain/extraction.py` and adds cost without clear value.

**Implication:** Set `MUNINN_GOOGLE_KEY` env var on MuninnDB server. Do NOT set `MUNINN_ENRICH_URL`. Graph richness comes from usage, not preprocessing.
