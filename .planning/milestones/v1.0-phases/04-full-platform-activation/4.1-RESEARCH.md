### Pattern 1: Async REST Client Wrapper
**What:** A thin async class wrapping MuninnDB REST API via httpx
**When to use:** All MuninnDB interactions from brain MCP server
**Example:**
```python
# Source: Verified against running MuninnDB v0.3.6-alpha REST API
import httpx
from typing import Optional

class MuninnClient:
    """Async REST client for MuninnDB."""

    def __init__(
        self,
        base_url: str = "http://localhost:8475",
        token: Optional[str] = None,
        timeout: float = 5.0,
    ):
        headers = {}
        if token:
            headers["Authorization"] = f"Bearer {token}"
        self._client = httpx.AsyncClient(
            base_url=base_url,
            headers=headers,
            timeout=timeout,
        )
        self._vault = "zbrain-vault"

    async def health(self) -> bool:
        """Check if MuninnDB is reachable."""
        try:
            r = await self._client.get("/api/health")
            return r.status_code == 200
        except httpx.HTTPError:
            return False

    async def write(
        self,
        concept: str,
        content: str,
        tags: list[str] | None = None,
        confidence: float = 0.9,
    ) -> str:
        """Write an engram. Returns ULID string ID."""
        r = await self._client.post("/api/engrams", json={
            "vault": self._vault,
            "concept": concept,
            "content": content,
            "tags": tags or [],
            "confidence": confidence,
        })
        r.raise_for_status()
        return r.json()["id"]

    async def write_batch(
        self,
        engrams: list[dict],
    ) -> list[dict]:
        """Write multiple engrams. Returns list of {index, id, status}."""
        r = await self._client.post("/api/engrams/batch", json={
            "vault": self._vault,
            "engrams": engrams,
        })
        r.raise_for_status()
        return r.json()["results"]

    async def activate(
        self,
        context: list[str],
        max_results: int = 10,
        threshold: float = 0.1,
    ) -> dict:
        """Run ACTIVATE cognitive retrieval pipeline."""
        r = await self._client.post("/api/activate", json={
            "vault": self._vault,
            "context": context,
            "max_results": max_results,
            "threshold": threshold,
        })
        r.raise_for_status()
        return r.json()

    async def close(self):
        await self._client.aclose()
```

**What:** Every MuninnDB call wrapped in try/except, libSQL/MuninnDB path always succeeds
**When to use:** All dual-write and parallel-search operations

### Pattern 3: Parallel Search with Source Labels
**What:** Query both pgvector and MuninnDB ACTIVATE, merge results with source labels
**When to use:** During the parallel trial period in `_handle_search`
**Example:**
```python
# In _handle_search: parallel retrieval pattern
async def _handle_search(args):
    query = args.get("query", "").strip()
    limit = int(args.get("limit", 10))

    # Run both searches in parallel
    pg_task = asyncio.create_task(_pgvector_search(query, limit))
    muninn_task = asyncio.create_task(_muninn_activate(query, limit))

    pg_results = await pg_task
    try:
        muninn_results = await muninn_task
    except Exception:
        muninn_results = []

    # Format with source labels
    lines = [f"# Search Results for: {query}\n"]
    lines.append("## pgvector Results")
    for r in pg_results:
        lines.append(f"- [pgvector] (sim: {r['similarity']:.2f}) {r['content'][:200]}")

    lines.append("\n## MuninnDB ACTIVATE Results")
    for r in muninn_results:
        lines.append(f"- [muninn] (score: {r['score']:.2f}) {r['content'][:200]}")

    return [TextContent(type="text", text="\n".join(lines))]
```

### Anti-Patterns to Avoid
- **Calling MuninnDB synchronously:** The brain MCP server is async. Use `await` for all httpx calls. Never use `requests` or synchronous httpx.
- **Failing the whole capture if MuninnDB is down:** MuninnDB is alpha software. libSQL/MuninnDB capture MUST succeed independently. MuninnDB is best-effort.
- **Generating embeddings client-side for MuninnDB:** MuninnDB handles its own embeddings server-side via `MUNINN_GOOGLE_KEY`. Do NOT pass embeddings in the REST API call.
- **Using the Python SDK (`from muninn import MuninnClient`):** Broken on Python 3.14. The `muninn-python` package installs zero code files.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| HTTP client with retries | Custom retry loop | httpx with timeout config | httpx handles connection pooling, timeouts, async natively |
| Embedding generation for MuninnDB | Client-side Gemini embed calls | MuninnDB server-side embedder (MUNINN_GOOGLE_KEY) | MuninnDB generates embeddings internally when configured |
| Vault creation | REST API call | CLI: `muninn vault create zbrain-vault --public` | CLI handles auth/config properly; REST admin API needs admin auth |

**Key insight:** MuninnDB is designed as a "batteries included" server. It handles embeddings, decay, Hebbian learning, and graph traversal internally. The client's job is simply to write engrams and call ACTIVATE. Do not replicate cognitive features client-side.

## Common Pitfalls

### Pitfall 1: SDK Installation Appears to Succeed But Doesn't Work
**What goes wrong:** `pip install muninndb` succeeds, `from muninn import MuninnClient` fails with ImportError
**Why it happens:** `muninn-python` v0.2.5 installs zero actual .py files on Python 3.14 (packaging bug in wheel)
**How to avoid:** Use direct httpx REST API calls instead. Do NOT depend on the SDK.
**Warning signs:** `pip show muninn-python` shows package installed but `RECORD` has only dist-info files

### Pitfall 2: No Embedder Configured = No Semantic Search
**What goes wrong:** ACTIVATE returns results but `semantic_similarity: 0` in score_components. Only full-text search works.
**Why it happens:** MuninnDB starts with `"no embedder configured, semantic similarity disabled"` warning (confirmed in log)
**How to avoid:** Set `MUNINN_GOOGLE_KEY` env var BEFORE starting MuninnDB. Requires server restart.
**Warning signs:** `index_size: 0` in `/api/stats`, `semantic_similarity: 0` in ACTIVATE responses

### Pitfall 3: Auto-Created Vaults Are Locked
**What goes wrong:** Writing an engram to a non-existent vault auto-creates it, but it becomes locked (requires API key)
**Why it happens:** MuninnDB defaults to "fail-closed" -- unconfigured vaults require API keys
**How to avoid:** Create vaults explicitly via CLI: `muninn vault create zbrain-vault --public`
**Warning signs:** `{"code":"VAULT_LOCKED","error":"vault requires an API key"}`

### Pitfall 4: Concept vs Content Confusion
**What goes wrong:** Putting all text in `content` and leaving `concept` empty, or vice versa
**Why it happens:** Unclear what each field is for
**How to avoid:** `concept` = short label/summary (first ~100 chars). `content` = full text. Both participate in search but concept is weighted differently in ACTIVATE scoring.
**Warning signs:** Poor ACTIVATE result quality

### Pitfall 5: MuninnDB Server Not Running
**What goes wrong:** All REST calls fail with connection refused
**Why it happens:** MuninnDB is not auto-started (deferred to Phase 4.4). Manual start required.
**How to avoid:** Health check on MCP server startup, log warning if MuninnDB is unreachable. Graceful degradation.
**Warning signs:** `httpx.ConnectError` on first call

```python

async def _handle_search(args):

            score = r.get("score", 0)
            lines.append(f"**{i}.** [muninn] (score: {score:.2f}) {r.get('content', '')[:200]}")
```

## Integration Patterns

### 1. Dual-Write to Capture (MCP `capture` tool)
**Where:** `_handle_capture()` in `mcp_server.py` (line 566)
**How:** After existing libSQL/MuninnDB insert + embedding, add MuninnDB write as best-effort
**Field mapping:**

| brain.memories | MuninnDB engram | Notes |
|---------------|-----------------|-------|
| content | content | Full text, 1:1 |
| content[:100] | concept | First 100 chars as short label |
| domain | tags[0] | Domain name as first tag |
| tags | tags | Append after domain tag |
| -- | confidence | Default 0.9 |
| -- | vault | Always "zbrain-vault" |

### 2. Parallel Retrieval in Search (MCP `search` tool)
**Where:** `_handle_search()` in `mcp_server.py` (line 642)
**How:** Run pgvector search and MuninnDB ACTIVATE concurrently via `asyncio.gather`

## Risks and Gotchas

### Risk 1: Python SDK Broken on Python 3.14
**Severity:** HIGH (confirmed)
**Impact:** Cannot use `from muninn import MuninnClient`
**Mitigation:** Use httpx REST API directly. Already validated working.
**Status:** RESOLVED by architecture decision

### Risk 2: Embedder Not Configured
**Severity:** HIGH (confirmed)
**Impact:** MuninnDB ACTIVATE uses full-text search only, no semantic similarity
**Mitigation:** Set `MUNINN_GOOGLE_KEY` env var, restart MuninnDB, run `vault reembed`
**Status:** Must be done in Phase 4.1 setup task

### Risk 3: MuninnDB is Alpha Software (v0.3.6-alpha)
**Severity:** MEDIUM
**Impact:** Potential bugs, API changes, crashes
**Mitigation:** Graceful degradation pattern. libSQL/MuninnDB is always the source of truth. MuninnDB failures never block capture or search.
**Status:** Addressed by architecture (parallel trial, brain wraps everything)

### Risk 4: Async Context in MCP Server
**Severity:** LOW
**Impact:** MCP tool handlers are already async, but lazy singletons are sync
**Mitigation:** Initialize httpx.AsyncClient lazily on first async call, not at import time
**Status:** Standard async pattern

### Risk 5: Embedding Model Mismatch
**Severity:** LOW-MEDIUM
**Impact:** If MuninnDB uses a different embedding model than pgvector, search quality comparisons are apples-to-oranges
**Mitigation:** The `MUNINN_GOOGLE_KEY` likely maps to a Google embedding model, possibly matching `gemini-embedding-001`. Verify after configuration by checking `/api/stats` for `index_size > 0` and ACTIVATE responses for `semantic_similarity > 0`.
**Status:** Verify during implementation

### Risk 6: Batch Limit Unknown
**Severity:** LOW
**Impact:** Web search mentioned "batch up to 50 memories in a single call" but not verified
**Mitigation:** With only 18 memories to seed, this is not a concern. For future scaling, test with larger batches.
**Status:** Not a blocker (18 << 50)

   - What we know: CONTEXT.md says add `activate` as tool #13. `search` gets parallel results during trial.
   - What's unclear: Whether Claude should call `activate` directly or only through the enhanced `search`.
