What MuninnDB is NOT:
Not a vector store. Not a RAG wrapper. Not a graph database. Not a filing cabinet with search.

What MuninnDB IS:
A storage engine that implements cognitive memory as math primitives — the way a brain actually works. This is why it makes intuitive sense for a second brain: a real brain doesn't store data, it learns from patterns, forgets what doesn't matter, and strengthens connections between things that fire together.


THREE CORE PRIMITIVES
---------------------

1. EBBINGHAUS DECAY (Recency)
Memories fade over time unless reinforced. Priority score computed at query time:
B(M) = ln(n+1) - d x ln(ageDays/(n+1))

Fresh + frequently accessed memories surface first. Old + unused memories fade but never delete. Deterministic — same inputs, same score, every time.

2. HEBBIAN LEARNING (Association)
"Neurons that fire together, wire together" — as database math.

When two memories are retrieved together, their association strengthens automatically. Co-activation log (50-entry ring buffer) feeds a background worker. Bidirectional weighted links between engrams. Strong associations can rescue faded memories. Links form from usage — not from manual design.

This is automatic mind-mapping. You don't build the graph. The graph builds itself from how you actually use the system.

3. BAYESIAN CONFIDENCE
Every memory has a confidence score (0-1). Contradictory information lowers confidence. Consistent reinforcement raises it. The database tracks belief strength, not just existence.


THE ACTIVATE PIPELINE
---------------------
Primary query type. Six parallel phases, all under 20ms:

Phase 1: Embed + tokenize the context string
Phase 2: Parallel retrieval — BM25 full-text search + HNSW vector search + decay-filtered pool
Phase 3: RRF fusion of three result lists
Phase 4: Hebbian boost from co-activation weights
Phase 5: BFS graph traversal (depth 2, hop penalty scoring)
Phase 6: Composite score + "Why" explanation builder

Every ACTIVATE call is both retrieval AND a learning event. Hebbian weights update on every query. The database gets smarter with use — no application code required.

One ACTIVATE call replaces: full-text search + vector search + decay logic + association scoring + graph traversal.


KEY VOCABULARY
--------------
Engram: A memory trace. Contains concept, content, confidence (0-1), relevance score, and weighted associations to other engrams.
Vault: A namespace for engrams. One vault per user, project, or context.
muninn_guide: MCP tool that tells Claude how to use memory. Vault-aware. No manual prompting needed.
ERF: Engram Record Format. Three tiers — Hot (L1 cache), Warm (disk), Cold (archive).

INTELLECTUAL FRAMEWORK
----------------------
MuninnDB implements what these thinkers described theoretically — not as metaphor, as math.

HERMANN EBBINGHAUS (1885)
Core idea: Memory decays predictably over time unless reinforced. The forgetting curve.
In MuninnDB: The decay primitive. Engrams fade by math, not by deletion.
For zbrain: Don't worry about managing what zbrain remembers. The system handles recency automatically.

GEORGE MILLER (1956)
Core idea: Human working memory holds 7 (+/-2) items. We need external systems to extend cognitive bandwidth.
In MuninnDB: ACT-R temporal weighting surfaces the most relevant memories so zbrain doesn't flood context with everything it knows.
For zbrain: MuninnDB is the cognitive offloading system. It handles what to surface so you don't have to manage it.

DOUGLAS HOFSTADTER
Core idea: Strange loops. Patterns that activate other patterns. Meaning emerges from recursive self-reference.
In MuninnDB: Hebbian recursion. Engrams that fire together strengthen each other. Chains of association create emergent meaning.
For zbrain: The longer zbrain runs, the richer the associations become. Meaning accumulates without being designed.

MARVIN MINSKY — Society of Mind
Core idea: The mind is not one thing — it's a society of competing agents. No central decider. Intelligence emerges from competition.
In MuninnDB: Engrams actively compete for relevance via composite scoring. No single memory dominates. The most relevant surface.
For zbrain: zbrain doesn't have one "memory." It has a society of memories that compete to be relevant.

ANDY CLARK — Extended Mind Theory
Core idea: Cognition doesn't happen only in the skull. We think with our tools, our notebooks, our environment.
In MuninnDB: MuninnDB is outside zbrain but part of how it thinks. Not a database backend — a cognitive substrate.
For zbrain: zbrain + MuninnDB is one thinking system. The boundary between the AI and its memory is dissolved.

EDWARD DE BONO — Lateral Thinking
Core idea: The mind is a self-organizing patterning system. Patterns form from experience, not design. Lateral thinking disrupts dominant patterns to find new paths.
In MuninnDB: Associations emerge from usage. The graph is never manually designed — it self-organizes around what actually fires together.
For zbrain: Don't try to architect how zbrain connects ideas. Use it. The connections will form themselves.

CHRISTOPHER ALEXANDER — Centers and Wholeness
Core idea: Living structure emerges when centers strengthen each other. Wholeness is not designed top-down — it grows from the interaction of parts.
In MuninnDB: Hebbian weights create a living structure of associations. Each query strengthens related engrams. The whole becomes more coherent with use.
For zbrain: This is why MuninnDB made immediate intuitive sense to Zack. It IS Alexander's architecture applied to cognitive infrastructure. Centers (engrams) strengthen each other through co-activation. Wholeness (coherent memory) emerges from use.

COMPARISON TO ALTERNATIVES
---------------------------
vs. Mem0/MemGPT/Zep/Letta: Memory wrappers using LLMs for extraction + vector stores. No engine-level cognitive primitives.
vs. Postgres: Stores data. MuninnDB stores memory that evolves with use.
vs. Vector DBs: Cosine similarity only. MuninnDB adds temporal weighting, Hebbian boosts, Bayesian confidence.
vs. Graph DBs: Model relationships you define. MuninnDB learns associations from usage automatically.
